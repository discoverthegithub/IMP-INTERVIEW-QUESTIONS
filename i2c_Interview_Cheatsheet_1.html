2. OOP Concepts (high-probability MCQs)

ConceptDefinition
EncapsulationBundling data + methods together, restricting direct access to internal state (private/protected).
AbstractionHiding implementation details, exposing only what's necessary (interfaces, abstract classes).
InheritanceA class derives properties/behavior from a parent class.
PolymorphismSame method name behaves differently depending on the object (method overriding) or same name, different parameters (overloading).

Commonly confused pairs

  • Overloading vs Overriding: Overloading = same method name, different parameters, same class (compile-time). Overriding = subclass redefines parent method, same signature (runtime).
  • Abstract class vs Interface: Abstract class can have some implemented methods + state. Interface (traditionally) only declares methods, no state.
  • Composition vs Inheritance: Composition = "has-a" relationship (object contains another object). Inheritance = "is-a" relationship.

3. Database Concepts

Normalization

FormRule
1NFAtomic values only, no repeating groups/columns.
2NF1NF + no partial dependency (non-key column depends on entire composite key, not just part of it).
3NF2NF + no transitive dependency (non-key column doesn't depend on another non-key column).

Keys

  • Primary Key: Uniquely identifies a row, cannot be null.
  • Foreign Key: References a primary key in another table, enforces referential integrity.
  • Composite Key: Two or more columns together form a unique identifier.

Joins

JoinReturns
INNER JOINOnly matching rows in both tables.
LEFT JOINAll rows from left table + matches from right (NULL if no match).
RIGHT JOINAll rows from right table + matches from left.
FULL OUTER JOINAll rows from both, matched where possible.

ACID Properties (likely to be asked directly)

  • Atomicity — transaction is all-or-nothing.
  • Consistency — database moves from one valid state to another.
  • Isolation — concurrent transactions don't interfere with each other.
  • Durability — once committed, changes survive even a crash.

Indexing

Speeds up read queries (SELECT) by avoiding full table scans, but slows down writes (INSERT/UPDATE/DELETE) since the index also needs updating. Trade-off: read speed vs write speed + storage.

5. Performance Testing — Core Domain Knowledge

This role is specifically Performance Testing, not general dev. Expect MCQs to lean into this domain more than a typical fresh-grad test.

Key Concepts

  • Load Testing: system behavior under expected user load.
  • Stress Testing: pushing beyond normal capacity to find the breaking point.
  • Spike Testing: sudden, sharp increase in load.
  • Soak/Endurance Testing: system under sustained load over a long period — checks for memory leaks, degradation.
  • Capacity Testing: maximum load a system can handle before performance degrades unacceptably.
  • Bottleneck: the component (CPU, memory, disk I/O, network, DB) limiting overall system performance.

JMeter Basics

  • Open-source load testing tool (Apache JMeter), primarily for web apps / APIs.
  • Core elements: Thread Group (simulates users), Sampler (the actual request, e.g. HTTP Request), Listener (view results — graphs, tables), Assertion (validate response correctness).
  • Common metrics reported: response time, throughput, error rate, latency.

Shell Scripting Basics (likely to have direct MCQs)

OS Basics

  • Process vs Thread: Process = independent program with own memory space. Thread = lightweight unit within a process, shares memory with other threads in that process.
  • Deadlock: two or more processes waiting on each other's resources indefinitely. Four conditions: mutual exclusion, hold and wait, no preemption, circular wait.
  • Virtual Memory: lets a process use more memory than physically available, via paging/swapping to disk.
  • Paging: dividing memory into fixed-size blocks to avoid fragmentation.

Network Basics

  • TCP vs UDP: TCP = connection-oriented, reliable, ordered (used for HTTP, file transfer). UDP = connectionless, faster, no delivery guarantee (used for streaming, gaming).
  • HTTP status codes: 2xx success, 3xx redirect, 4xx client error, 5xx server error. Know 200, 301, 404, 500 at minimum.
  • DNS: translates domain names to IP addresses.
  • Latency vs Throughput: Latency = time for one request to complete. Throughput = number of requests handled per unit time. A system can have low latency but low throughput, or vice versa — don't confuse the two.

SDLC & QA Methodologies

  • SDLC phases: Requirements → Design → Implementation → Testing → Deployment → Maintenance.
  • Waterfall vs Agile: Waterfall = sequential, rigid phases. Agile = iterative sprints, adapts to change.
  • Types of testing: Unit (individual component), Integration (components together), System (whole application), UAT (user acceptance, real-world validation), Regression (re-test after changes to confirm nothing broke).
  • Black-box vs White-box testing: Black-box = tester doesn't see internal code, tests input/output. White-box = tester sees and tests internal logic/code paths.

5b. SQL — Query Basics (high-probability MCQ area)

Core syntax

SELECT column1, column2 FROM table_name WHERE condition;
INSERT INTO table_name (col1, col2) VALUES (val1, val2);
UPDATE table_name SET col1 = val1 WHERE condition;
DELETE FROM table_name WHERE condition;

Aggregate functions

FunctionPurpose
COUNT()Number of rows
SUM()Total of a numeric column
AVG()Average value
MAX() / MIN()Highest / lowest value

GROUP BY vs HAVING vs WHERE

  • WHERE filters rows before grouping.
  • GROUP BY groups rows sharing a value into summary rows.
  • HAVING filters groups after aggregation (WHERE can't be used with aggregate functions like COUNT/SUM directly — that's what HAVING is for).
SELECT department, COUNT(*) FROM employees
WHERE status = 'active'
GROUP BY department
HAVING COUNT(*) > 5;

DDL vs DML vs DCL vs TCL

CategoryCommandsPurpose
DDLCREATE, ALTER, DROP, TRUNCATEDefines structure (schema)
DMLSELECT, INSERT, UPDATE, DELETEManipulates data
DCLGRANT, REVOKEAccess control/permissions
TCLCOMMIT, ROLLBACK, SAVEPOINTTransaction control

Common traps in MCQs

  • DELETE vs TRUNCATE vs DROP: DELETE removes rows (can use WHERE, can rollback if in transaction). TRUNCATE removes all rows fast, resets identity, can't use WHERE, harder to rollback. DROP removes the entire table structure.
  • WHERE vs HAVING: classic trap — remember WHERE can't filter on aggregate results, HAVING can.
  • UNION vs UNION ALL: UNION removes duplicates, UNION ALL keeps them (and is faster since it skips the dedup step).

6. Essay Writing — Practice Plan for Tonight

You flagged this yourself: mind thinks in Urdu/mixed language, writing in English slows you down, and this is a graded communication check with no AI allowed. This needs deliberate practice tonight, not just reading tips.

Structure to memorize (use for ANY topic they give you)

  1. Intro (3-4 sentences): State the topic, your position/stance clearly, and briefly preview your 2-3 supporting points.
  2. Body Paragraph 1: One clear point + one concrete example or reason supporting it.
  3. Body Paragraph 2: Second point, ideally a different angle (not repeating point 1 in different words).
  4. Body Paragraph 3 (optional, if time allows): Counter-argument + why your position still holds — this shows analytical depth, which is explicitly graded.
  5. Conclusion (2-3 sentences): Restate your position, summarize briefly, end with a forward-looking or broader statement.

What graders are actually scoring — map your effort here

  • Ideas & analysis: Don't just describe the topic — take a clear stance and analyze why, not just what.
  • Development & support: Every claim needs a reason or example. Don't leave a statement floating unsupported.
  • Organization: Stick to the paragraph structure above. A grader should be able to tell where your intro ends and each point begins.
  • Language & conventions: Simple, correct sentences beat complex, error-filled ones. Don't reach for big words you're unsure of — clarity scores higher than vocabulary.

7. Sample Essays — Full Written Examples

These are model answers, not something to memorize word-for-word — the real prompt will be worded differently. Study the structure, sentence length, and how each paragraph does exactly one job. Then write your own version by hand, in your own words, using your real details.

Sample 1 — Prompt: "Describe a time you had to overcome an unexpected setback in a team project. What did you learn?"

During my final year project, my team was responsible for building a mobile health application that combined a machine learning model with a mobile front end. Midway through the semester, one of my project partners became unavailable due to personal reasons and was unable to continue contributing to the assigned modules. This left a gap in the project at a stage when the deadline was already fixed and could not be extended.

Rather than waiting for the situation to resolve itself, I reorganized the remaining work between the active team members. I took on the modules that had been left incomplete, in addition to my own responsibilities, and set a stricter internal schedule to make sure each component was tested before integration. I also began checking in with my supervisor more frequently, so that any further delays would be visible early rather than discovered close to submission.

Looking back, I learned that clear task ownership from the very beginning of a project matters more than I had assumed. If responsibilities and expected contributions had been documented explicitly at the start, the transition when a team member became unavailable would have been smoother. I now apply this lesson by defining clear scope and check-in points at the start of any group work, rather than assuming informal coordination will be enough.

This experience did not just teach me how to complete a project under pressure — it taught me that reliability is something you build into a plan in advance, not something you rely on from other people alone.

Sample 2 — Prompt: "Write about a time a plan didn't go as expected and how you responded."

A few days before an important project submission, my laptop stopped working correctly, and I was unable to access it for several hours during a period when I still had testing and final adjustments to complete. At that point in the project, most of my recent work existed only on that machine, and the deadline did not move to accommodate the disruption.

My first step was to check what could still be recovered. Because I had been pushing my code to GitHub regularly, I was able to retrieve the most recent working version of my project from there rather than starting over. I then arranged to use another computer to continue the remaining work, and prioritized the most critical remaining tasks first, in case time ran short again.

The situation was resolved without losing significant progress, but it made clear to me how easily a single point of failure can put an entire project at risk. Since then, I have made version control and regular backups a standard part of how I work, rather than something I do only when I remember to.

What this experience taught me is that planning for failure is as important as planning for success. Systems and habits that seem like extra effort in the moment — like committing code frequently — are often what actually protect the work when something goes wrong unexpectedly.

Sample 3 — General topic: "Is discipline more important than talent for success?"

Talent is often treated as the deciding factor in success, but in practice, discipline plays a far larger role in determining who actually achieves long-term results. Talent may explain why someone starts strong, but it rarely explains why someone continues improving over months or years.

Consider two people learning the same skill. The more talented person may progress faster in the beginning, but without consistent effort, that early advantage tends to fade. The person who shows up regularly, practices even when progress feels slow, and corrects their mistakes over time will typically overtake a naturally gifted but inconsistent counterpart. This pattern appears across fields, from academics to sports to professional work.

Discipline also compensates for a lack of natural ability in ways that talent alone cannot replace. A less naturally skilled person who works steadily can close the gap over time, while raw talent without effort tends to plateau. This does not mean talent is irrelevant — it can accelerate progress — but it is not sufficient on its own.

In conclusion, while talent may open doors early, discipline is what allows someone to walk through them and keep moving forward. Long-term success depends less on where someone starts and more on how consistently they choose to keep working.

  3. Compare your version to the sample only after finishing — check structure and clarity, not word-for-word similarity.
