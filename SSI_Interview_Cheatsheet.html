Polymorphism — they go deep here
  • Static binding (compile-time) → function overloading — same name, different params, resolved at compile time
  • Dynamic binding (runtime) → function overriding via virtual — resolved at runtime based on object type
  • Early binding = overloading  |  Late binding = overriding
// Overloading - static/early binding
int add(int a, int b)    { return a+b; }
double add(double a, double b) { return a+b; }

// Overriding - dynamic/late binding
class Animal { virtual void speak() { cout<<"..."; } };
class Dog : public Animal {
  void speak() override { cout<<"Woof"; }
};
Animal* a = new Dog();
a->speak(); // "Woof" — resolved at runtime
Interview line: "Overloading is resolved at compile time (static), overriding is resolved at runtime (dynamic) via virtual functions."

Bank Transaction Story (tell this exact story)
Q: What happens when bank transfer fails mid-way?

Money is debited from Account A, then network error — Account B never gets it. Database uses transactions + rollback: if any step fails, ALL changes undo automatically (Atomicity). The balance goes back to original. This is why BEGIN/COMMIT/ROLLBACK exist.

BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- both succeed → saved
-- ROLLBACK;  if error → both undo

FormRule
1NFatomic values, no repeating groups
2NF1NF + no partial dependency on composite key
3NF2NF + no transitive dependency (non-key → non-key)
They may give you a raw table and ask you to normalize it. Rule of thumb: if you see repeated data across rows, it needs to be split into a separate table.
Indexing — why it matters
  • Without index → full table scan → O(n)
  • With index → B-tree lookup → O(log n)
  • Add index on columns used in WHERE, JOIN, ORDER BY
  • Trade-off: faster reads, slower writes (index must update)
CREATE INDEX idx_user_email ON users(email);
-- now WHERE email='...' uses index, not full scan

SQL — High Frequency Queries

HIGH
JOINs
-- Get all orders with customer name
SELECT c.name, o.amount
FROM customers c
JOIN orders o ON c.id = o.customer_id;

-- LEFT JOIN: keep all customers
-- even if no orders
SELECT c.name, o.amount
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id;
GROUP BY + HAVING + Aggregates
-- Highest salary per department
SELECT dept, MAX(salary) AS max_sal
FROM employees
GROUP BY dept;

-- Depts with avg salary > 50k
SELECT dept, AVG(salary)
FROM employees
GROUP BY dept
HAVING AVG(salary) > 50000;
Subqueries + Date Filters
-- Top scorer name
SELECT name FROM students
WHERE score = (SELECT MAX(score)
               FROM students);

-- Last 30 days orders
SELECT * FROM orders
WHERE created_at >= 
  DATE_SUB(NOW(), INTERVAL 30 DAY);

-- Top 3 records
SELECT * FROM sales
ORDER BY amount DESC LIMIT 3;
WHERE vs HAVING: WHERE filters rows BEFORE grouping. HAVING filters AFTER GROUP BY. You cannot use aggregate functions in WHERE.

Optimization — "API is 15 seconds slow, what do you do?"

HIGH — scenario question
1. Database
  • Add indexes on WHERE/JOIN columns
  • Select only needed columns — no SELECT *
  • Avoid N+1 queries → use JOINs or eager loading
  • Add pagination — don't return 10k rows at once
-- Bad: returns 10k records
SELECT * FROM users;

-- Good: paginated
SELECT id, name FROM users
LIMIT 20 OFFSET 0;
2. Caching
  • Store repeated data in Redis / memory
  • First call → hit DB, save to cache
  • Next calls → return from cache instantly
# Redis example (Python)
def get_users():
  cached = redis.get('users')
  if cached: return cached
  
  data = db.query('SELECT * FROM users')
  redis.set('users', data, ex=300)
  return data
3. Load Balancing + Async
  • Load balancer distributes traffic across multiple servers
  • Heavy tasks → run in background queue (Celery, RabbitMQ)
  • Return immediate response, process async
# Architecture
User → Load Balancer
         ↓
  Server1 / Server2 / Server3
         ↓
     Database (shared)

# Async queue
POST /send-email → return 202
  → Celery processes in background
COMPLETE ANSWER — say exactly this

"If an API is slow, I'd first profile it to find the bottleneck. Then: add database indexes on filtered columns, implement caching with Redis for repeated data, add pagination to limit response size, push heavy tasks to a background queue, and add load balancing to distribute traffic across servers."

OSI Layers — quick recall
  • 7 Application — HTTP, DNS, SMTP
  • 4 Transport — TCP/UDP, ports
  • 3 Network — IP, routing
  • 2 Data Link — MAC, Ethernet
HTTPS / TLS in 3 lines
  • Client says hello, server sends certificate (public key)
  • Client verifies cert, sends symmetric key encrypted with public key
  • Both use symmetric key (AES) for fast encrypted data transfer
DNS resolution
  • Browser cache → OS cache → ISP resolver → Root → TLD → Authoritative → IP returned
  • DNS uses UDP port 53
